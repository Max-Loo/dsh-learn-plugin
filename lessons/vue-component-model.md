## 钟面摆正

先把这只机器的全部零件再放一遍（你已经建立的，我只是摆整齐）：

> 接收方只有**一个寄存器**（指针）。
> 收到 seq == 指针 → **交付，指针走一格**。
> 其余一切 → **丢弃、补 ACK，指针不动**。

关键在「走一格」的几何：8 个刻度**围成一个环**。在这个环上，每个刻度都有两个邻居——**7 和 0 是贴着的**。沿 0→1→2→…的方向走，7 的下一格就是 0：

$$7 + 1 \equiv 0 \pmod 8$$

没有第三种可能：不是 8（钟面上**没有** 8 这个刻度可指），更不是原地不动——「不动」是「不相等就丢弃」那条规则的事，跟「交付后走一格」是两条独立的规则，上次它们在你脑子里黏在了一起。

这和你已经走通的 $3 + 1 \equiv 0 \pmod 4$ 是**同一句话**——只是钟面从 4 格大到了 8 格。

## 修复：两个论证

**论证一：你已经走对过这只机器。** 昨晚那只 4 刻度钟（0,1,2,3），指针在 3，交付 seq 3——你答对了：**下一格是 0**，不是 1。同一台机器，不可能 4 个刻度时回到 0、换成 8 个刻度就走到 1。「转满一圈回到哪」的答案由**起点**决定，不由钟的大小决定。

**论证二：「8」不是新刻度——它就是 0 这个刻度的另一个名字。** 数一下这只钟：0, 1, 2, …, 7——**一共 8 个刻度**。从 0 出发走 8 格，恰好绕环一周，落回出发的那个位置：

$$8 \equiv 0 \pmod 8$$

为什么你的直觉会说「1」？因为现实挂钟走满一圈是 12→**1**——但那是现实钟**没有 0 刻度**造成的（它从 1 数到 12）。这只钟**有 0**：会话一开始，发送方发出的第一个包就是 seq **0**，接收方的指针初始化时指的就是 **0**——它等着第一个包。0 是这只钟的起点；转满一圈，回到的就是它。

对着图核对一遍：顶部那个刻度标的是 **0**（不是 12），它左边贴着的 7 走一格到它。整条环上没有任何位置叫 8，也没有任何规则让回卷跳过 0 落到 1。

## 你把序号空间看成一条线——但它是一只环

「0, 1, 2, …, 7」在你的模型里是**一列队伍，7 站在队尾**。队尾之后没有位置，所以指针「走不出去」——停在 7，或者慌乱中跳到 1。但你看图里那只钟：**没有队尾**。8 个刻度首尾相接围成一圈，7 的肩膀后面贴着的就是 0。线上才有「终点之后不动」；环上**没有终点**，每一格都有下一格。

## 为什么必须是 0——不是约定，是机器能转下去的唯一解

这次我不讲几何，讲**功能**。问你自己一个问题：

> 发送方发完 seq 7 之后，流水线继续转，它的**下一个新包**用哪个序号？

发送方的序号寄存器和接收方的指针，是**同一只钟的两份拷贝**——接收方持续接受的条件是「seq == 指针」，所以两份拷贝必须一步一步走同一条轨迹。现在逐个检验四个候选：

- **停在 7** → 发送方下一个包是 seq 0（第二圈从 0 开始编号），但接收方指针卡在 7：$0 \neq 7$，**第二圈的第一个包被永远丢弃**。机器死锁，课程结束。
- **走到 1** → 发送方发 seq 0，指针却指 1：$0 \neq 1$。错位一格，**永远错位**。同样死锁。
- **走到 8** → 钟面上**没有**这个刻度可指。
- **回到 0** → 发送方的下一个 seq 0 == 接收方指针 0。✓ 接受、交付、继续转。

只有第四种可能让「传输永不停止」这个你已经接受的事实成立。回卷到 0 是**流水线持续运转的逻辑必然**，不是谁规定的记号习惯。

## N1 后半：把失败变成定律

### 歧义的精确形状

昨晚你亲手推过那个失败：3 比特、窗口 8（0…7 全发）、8 个 ACK 全丢、指针走完一圈回到 0——旧 0 重传到达，$0 = 0$，被当新数据接受。你的结论当时就下对了：**旧 0 和新 0 在线路上逐位相同**。地基修好之后，这句话可以更锋利地说：

> 歧义 = **指针回卷撞上了「未确认、还在飞」的旧序号。**

两条消除它的路：

1. **显式相位标记**：给每个包加一圈数——(圈 2, seq 0) ≠ (圈 1, seq 0)，立刻可分。代价：**头部多花比特**，且任何固定宽度最终还是会回卷（TCP 的 32 位也会——只是周期长到撞不上）。
2. **约束窗口，一格都不加**。这就是要推导的定律。

### 推导：一格空档如何替代一个比特

问自己：**接收方指针要「再次指到 0」，路上必须先发生什么？**

指针从 0 出发走一整圈回到 0，中途必须**交付 seq 7**。而发送方要把 seq 7 发出来，它的窗口必须已经滑到包含 7——即窗口从 {0…6} 前移，而滑动的前提是**收到覆盖 seq 0 的 ACK**，也就是 **0 已被确认**。确认过的序号，GBN 发送方**永不重发**。串起来：

$$\text{指针回到 0} \;\Rightarrow\; \text{交付过 7} \;\Rightarrow\; \text{7 被发出} \;\Rightarrow\; \text{窗口滑过} \;\Rightarrow\; \text{0 已确认} \;\Rightarrow\; \text{旧 0 不再在飞}$$

**指针每次回到刻度 k，上一圈的 k 必然已确认、已注销。** 永不撞车——不需要任何额外比特。

现在看昨晚的 W=8 为什么断了这条链：窗口初始就是 {0…7}，**seq 7 不需要任何确认就能发出**——链子在第一环就断了。指针走完一圈回到 0 时，窗口从未滑动、0 从未确认、旧 0 还在天上飞。

**一格之差 = 「发 7 是否需要 0 先被确认」。** 于是定律：

$$W \le 2^n - 1$$

留出的那一格空档，就是「隐式的相位标记」——**花 1 个刻度的序号空间，省下显式圈数比特**。窗口定律不是安全边际，是恰好够用的精确边界。

## N2：让「砍一半」变成定理

### GBN 到底在为什么付钱

回看 N1 里你推过的满窗场景，GBN 的规则是：**接收方只认指针**（seq ≠ 指针一律丢弃），**发送方一超时就把窗口内未确认的全部重发**。摆一个具体损失——窗口 7，发 0…6，包 2 在路上蒸发，3,4,5,6 平安到达：

- 接收方：指针停在 2，$3,4,5,6 \ne 2$ → **全部丢弃**。四个完好到达的包，死在门口。
- 超时后发送方重发 **2,3,4,5,6**——其中四个是白给的重复。

丢 1 个，重发 5 个；信道越差，这个乘法越狠。直觉的修复方案就是你昨天那句名言的下半句：**只重发真正丢的那个**。

### SR（Selective Repeat）的三个改动

1. **接收方缓存乱序包**：seq 落在接收窗口内但 ≠ 指针 → 不丢弃，**存着**；指针补齐后一口气交付连续段。丢弃只留给「窗口外的旧重传」。
2. **逐包确认**：收到就 ACK，无论是否按序（不再等指针）。
3. **发送方独立计时器**：每个包各管各的超时，谁丢重发谁。

重传量收敛到「恰好丢失的量」。但你从 N1 已经有了嗅觉：**接收方开始收「指针之外」的包，意味着它也占序号空间了**。

### 代价：环上现在有两个玩家

GBN 的环上只有一个窗口（发送窗），留 **1** 格空档就买到安全（$W \le 2^n-1$）。SR 的环上有**两个**：发送窗（未确认、可重发）+ 接收窗（可缓存）。安全条件变成：**同一刻度，绝不能一边「还可能被重发」、一边「可能被接收方当新包缓存」**——即两窗覆盖之和不得超过环长：

$$W_{SR} \le \frac{2^n}{2} = 2^{n-1} \qquad (n=3:\ W \le 4)$$

**你那句「砍一半」，严格正确**——但注意它正确的原因不是「保守点好」，而是**几何必然**：接收窗口从 1 涨到 $W$，买的每一格都要从发送窗口的预算里扣。

验收题就是那个反例本身——盯着违规的 W=5 走一遍：

>
> 1. 被认出是旧一代，扔掉
> 2. 触发接收窗口收缩
> 3. 不等于指针，直接丢弃

> [!failure] Quiz — incorrect ✗
> Your answer: 1. 被认出是旧一代，扔掉
> Correct answer: 落在接收窗口内，被当作新 0 缓存
>
> SR 接收方对「窗口内、非指针」的包的动作是缓存——这正是它省重传的机关，但此刻反噬：旧 0 落在滑动后的接收窗 {5,6,7,0,1} 内，被当作新 0 存入，两代 0 混叠。这就是 W ≤ 2ⁿ⁻¹ 的由来：发送窗与接收窗覆盖之和一旦超过环长 8，同一刻度的两代就会同时「一边可被重发、一边可被缓存」。「不等于指针就丢弃」是 GBN 的规则，SR 早已不这么做事；「认出是旧的」需要接收方记住交付历史——你在摸底阶段亲手排除过这种魔法；「触发收缩」不存在这个机制。GBN 一个玩家留 1 格（2ⁿ−1），SR 两个玩家对半分（2ⁿ⁻¹=4）——砍一半，从直觉升格为定理。

## 修复：认不出，正是定律存在的原因

回到你自己建立过的第一原则。包上携带的全部身份是什么？**seq + 校验和**。而你昨天亲手推导过的结论原封不动：

> 旧 0 和新 0 在线路上**逐位相同**——序号都是 0，校验和都完好。

「认出这是旧一代」需要什么？需要一个「这是第几圈」的标记——**相位标记**。而你刚刚在 N1 学过：相位标记**要花比特，而我们没花**——$W \le 2^n-1$ 和 SR 对半分的全部出发点，就是「用几何换比特」。

所以把逻辑倒过来拧紧：

- 如果接收方**能**认出旧 0 → 根本不需要任何窗口约束，$W$ 想多大都行。
- 窗口约束**存在且必要** → 恰恰证明接收方**认不出**。

> **每一条安全约束的存在，都在为它所防御的无能作证。**

「认不出」不是 SR 的缺陷——它就是「不花圈数比特」这个决定的另一面。防线只剩几何：让两代同名包不可能同时「一边可被重发、一边可被缓存」。

## 击穿它：两个宇宙

**宇宙一**：旧 0 超时重传，走了一条顺路的线，先到；新 0（第二圈原发）后到。→ 后到的是**新的**。
**宇宙二**：新 0 原发走了近路，先到；旧 0 的重传绕了远路，后到。→ 后到的是**旧的**。

两个宇宙里接收方看到的**完全相同**：先一个 0，后一个 0。「谁先谁后」这个事实在两个宇宙里都成立，代数真相却相反——所以**先后顺序不携带代数信息**。原因很简单：旧 0 的重传和新 0 的原发**都**发生在第一圈原发之后，「晚于原发」对两代同时成立，分不出谁。

再挖一层——你这个直觉有真实出处：**停等协议里「重复到达 = 旧」确实成立**。但那不是「顺序」的功劳，是**窗口 = 1** 的功劳：任何时刻天上只有一代包，「重复」必然来自旧代。你把停等的遗产带进了 SR——而 SR 窗口变大后顺序失效的**那个位置**，恰好就是窗口约束（$W \le 2^{n-1}$）接管的位置。又是同一个模式：**顺序失效之处，几何接管**。

## 不可能性证明：「认出旧代」在逻辑上不成立

**第 1 步（你昨天自己走过的）**。接收方能依据的一切 = 它收到过的全部字节和全部到达事件。旧 0 与新 0 **逐位相同**——你昨天亲手推过这句。

**第 2 步（两个宇宙）**。构造 U1、U2：接收方从会话开始收到的一切——每个包的每个字节、每次到达的先后——**逐位、逐事件完全相同**。唯一差别是「真相」：U1 里先到的 0 是旧重传，U2 里它是新原发。

**第 3 步（规则的死刑）**。任何确定性规则 = 相同输入 → 相同输出。两个宇宙输入相同 → 规则给出**同一个**答案 → 而两个宇宙真相相反 → **至少在一个宇宙里判错**。无论规则多聪明——读历史、看顺序、辨模式——只要它读的是输入，而输入无差异，它就无差异。$\blacksquare$

这不是「还没找到办法」，是**办法在逻辑上不存在**。你昨天推出的「任何固定规则对逐位相同的输入只能取同一动作」就是这条证明的雏形——你没有忘它，只是没认出它在这里适用。

顺手把「整窗齐发模式」的具体漏洞也堵上：SR 是**逐包独立计时器**（三改动之一），旧 0 的重传本来就是孤零零一个包；就算整窗齐发，信道抖动（你摸底第一天就接受的「丢、重、乱」）也会把它抖散——**齐发不保证齐到**。模式，也是输入的函数；输入无差异，模式无差异。

## 既然认不出——就禁止这个状态本身

证明的真正用途在后半：既然区分不可能，唯一的出路是让 **U1/U2 这种局面根本无法出现**——即「两代同名包同时在飞」被禁止。执行禁止的就是窗口：$W \le 2^{n-1}$，发送窗与接收窗对分环面，**旧代尚未注销时新代的同名包发不出来**。这就是定律的全部身世：一条为「逻辑不可能性」兜底的几何禁令。

## 预算论证：空档和接收窗是同一笔钱的两种花法

环的预算只有一份：**环长 $2^n$ 个刻度**。看两张图：

- **GBN**：环上的消费者只有一个——发送窗 $W$，外加 **1 格空档**。合计 $W + 1 \le 2^n$，所以 $W \le 2^n - 1$。空档为什么是「空的」？因为 GBN 接收窗 $= 1$（只认指针那一格），**不占环面预算**。
- **SR**：环上有两个消费者——发送窗 $W$ **加接收窗 $W$**。合计 $W + W \le 2^n$，所以 $W \le 2^{n-1}$。**那个「空档的位置」没有消失——它被接收窗占掉了。**

看 SR 图上蓝弧与绿弧相抵的那两道接缝：GBN 的空档是**无人值守的隔离带**；SR 没有隔离带，因为**对面半环本身就是墙**——接收窗守在那里。同一格预算，GBN 花在空档上，SR 花在接收窗上；**不能花两次**。再留一格不是「更安全」，是给一笔已经花掉的预算记第二次账。

## SR 是什么

**SR = Selective Repeat（选择性重传）**，是可靠传输协议的一种设计。它是为解决 GBN（Go-Back-N）的浪费而生的：

- **GBN**：接收方只认「指针」位置的包，其余一律丢弃；发送方一超时就把整个窗口全部重发。丢 1 个包 → 重发 5 个，信道越差浪费越大。
- **SR 的三个改动**：接收方**缓存**乱序到达的包（不再丢弃，等缺口补上后一并交付）；逐包确认；发送方**每个包独立计时**，谁超时重发谁。重传量收敛到「恰好丢失的量」。

## 定律本身

$$W_{SR} \le \frac{2^n}{2} = 2^{n-1}$$

**n 比特序号下，SR 的发送窗口不得超过序号空间的一半。** 3 比特（8 个刻度）时 $W \le 4$；你卡住的那道题是 2 比特（4 个刻度），答案是 $W \le 2$。

## 为什么是一半

这是今晨推导到一半的地方：

1. SR 的接收方开始收「指针之外」的包 → **接收方也在序号环上占了一个窗口**（GBN 接收窗 = 1，不占环面）。
2. 危险：发送窗（旧包可能还在飞、可能被重发）与接收窗（可能把到达的包当新包缓存）一旦在环上**重叠**——旧一代的 seq 0 会被当作新一代的 seq 0 缓存，数据错乱。
3. 而「认出旧包」在逻辑上不可能——你已经验收过那个平行宇宙证明（两代包逐位相同，任何规则给出同一答案，必错其一）。
4. 所以唯一防线是**几何**：两窗覆盖之和不超过环长 $2^n$，即各占一半：

![SR 双窗口对分环面：发送窗与接收窗各占一半](viz/viz-sr-halving-20261021-074735.png)

对比 GBN 定律 $W \le 2^n - 1$（留 1 格空档）：同一条定理——**禁止两代同名包同时在飞**——环上有一个玩家时付 1 格，有两个玩家时对半分。

> [!question] Quiz
> 父组件把数组 items 通过 props 传给子组件。子组件的代码里直接写了 items.push(x)。这句话的实际后果是？
>
> 1. 改成功，但只改到子组件副本，父组件看不到
> 2. 改成功，父组件数据跟着变，开发模式警告
> 3. 改不了，编译直接报错，程序无法运行
> 4. 改不了，prop 是只读副本，push 静默失败


> [!success] Quiz — correct ✓
> Your answer: 2. 改成功，父组件数据跟着变，开发模式警告
> Correct answer: 改成功，父组件数据跟着变，开发模式警告
>
> props 传的是引用——子组件拿到的 items 和父组件是同一个数组对象，push 真的会成功、父组件数据真的会变、依赖它的界面真的会更新。「单向数据流」是设计约定，不是物理隔离：Vue 在开发模式警告你，因为它保护的不是「数据不被改」，而是「数据变化只沿一条路走」的可追踪性——谁改了什么，一眼可查。钻空子能得手，代价是失去可维护性。这正是「会用」与「理解设计」的分界。

✓ props 线的起点比自评高——你已经站在「约定 vs 物理隔离」的理解层。继续沿这条线向上探一题，同时探 emit 线的入口：


> [!question] Quiz
> 子组件里有个输入框，用户输入后需要更新父组件的数据 count。按 Vue 的设计，正确做法是？

> 1. 父组件把改数据的函数当 prop 传下来，子组件调用
> 2. 子组件 emit 事件，父组件监听并改自己的数据
> 3. 子组件直接修改 prop 的值
> 4. 子组件修改一个共享的全局变量


> [!success] Quiz — correct ✓
> Your answer: 2. 子组件 emit 事件，父组件监听并改自己的数据
> Correct answer: 子组件 emit 事件，父组件监听并改自己的数据
>
> emit 是 Vue 为「子→父」设计的正统通道，它和 props 一起构成单向数据流的完整闭环：数据向下（props）、事件向上（emit）——父组件拥有数据，就由父组件亲手改；子组件只报告「发生了什么」，不伸手改别人的数据。直接改 prop 是刚才确认过的钻空子；全局变量绕开组件树，任何组件都能暗改，不可追踪；把修改函数当 prop 传下来（callback prop）技术上完全可行——React 正是这么做的——但 Vue 选择了事件模型：模板里 @update="count = $event" 让「谁响应、怎么响应」留在父组件的声明式语法里，而函数传参把控制流拉回命令式。两种设计都能工作，取舍在声明式程度——这是「设计逻辑」环节的正题。

> 2. 内容在父作用域编译，保持结构化与安全
> 3. 纯为性能，字符串渲染更慢

> [!success] Quiz — correct ✓

> 2. 解构出来的值被冻结，不可变更
> 3. 响应性靠代理拦截属性访问，解构拿到的是脱离代理的普通值
> 4. 解构是浅拷贝，深层嵌套的数据会丢失


> [!success] Quiz — correct ✓
> Your answer: 3. 响应性靠代理拦截属性访问，解构拿到的是脱离代理的普通值

> 4. 两次——a 的两次合并，b 另算一次


> [!success] Quiz — correct ✓
> Your answer: 1. 一次——同一轮微任务里批量刷新，队列按组件去重
> Correct answer: 一次——同一轮微任务里批量刷新，队列按组件去重

> 修改触发 trigger 后，组件的渲染 effect 进入调度器队列——按组件去重，同一 effect 多次入队只保留一份——然后在微任务里统一刷。所以三次修改 = 一次重渲染，且渲染发生在当前同步代码跑完之后。「数据是同步的，DOM 是批量的」：这个调度设计牺牲「改完立刻看到 DOM」，换取 N 次修改 1 次渲染。需要改完立刻拿 DOM时的 nextTick()，等的就是刷队列那一拍微任务。

> [!question] Quiz
> 默认配置下（flush: 'pre'），watch(source, cb) 的回调 cb 执行时，组件 DOM 处于什么状态？
>
> 1. 渲染之前——回调里读到的是旧 DOM
> 2. 同步执行——数据一改立刻跑
> 3. 与渲染同拍完成，先后无保证
> 4. 渲染之后——回调里读到的是新 DOM


> [!question] Quiz — I don’t know
> Your answer: I don’t know
> Correct answer: 渲染之前——回调里读到的是旧 DOM
>
> 调度器内部有三个执行时机：pre（组件渲染前）、post（渲染后）、sync（同步立即）。watch 默认 flush: 'pre'——回调进 pre 队列，排在组件渲染 effect 之前执行，所以回调里查 DOM 拿到的是上一次的旧 DOM。要操作更新后的 DOM 需要 flush: 'post'（与 nextTick、updated 同期）；flush: 'sync' 跳过队列、数据一改立刻跑。这个三队列设计各司其职：pre 给你「渲染前修改派生状态」的窗口（避免一次多余的双渲染），post 服务「DOM 已就绪」的操作需求，sync 只留给确实需要强同步语义的场合。默认选 pre 而非 post，是因为多数 watch 的目的是同步派生状态而非读 DOM——再次是设计取舍，不是随手规定。

# N1 — flush 三队列

## Motivate：回到你那道 dontKnow

「watch 回调执行时，组件 DOM 处于什么状态？」你当时诚实地答了不知道——这道题表面是 API 细节，底下其实是**调度器的内部结构**。你已经握住「更新是微任务批量的」（摸底确认过：三次修改一次渲染），但「批量」的内部还有**秩序**——同一个微任务里，谁先谁后。三队列就是这个秩序。

## Establish：一次 flush 的完整解剖

![Vue 更新周期：同步代码 → 微任务主队列 → post 队列](viz/viz-vue-flush-timeline-20261021-091355.png)

从上往下读这张时间轴：

**第一段（同步代码）**：`state.a = 1; state.a = 2; state.b = 3`——数据同步改，什么都不渲染。唯一在这里跑的是 `flush: 'sync'` 的 watcher：**立即执行、不入队、无批处理**——改几次跑几次，官方警告别用在数组这类高频源上，原因你自己能推。

**微任务边界**：同步代码跑完，`Promise.resolve().then(flushJobs)` 启动 flush。`nextTick` 挂的就是这个 promise——「nextTick 等的那一拍」在这里有了确切坐标。

**第二段（主队列，按组件 id 升序）**：所有 job 排成一条队，**父组件先创建所以 id 更小，父先子后**。每个组件的节奏是：**pre watcher → 渲染 effect**。注意图中那两行灰色注释——**pre watcher 与它组件的更新 job 共享同一个 id，被二分插入到该 job 的紧前面**。「pre = 渲染之前」不是口号，是物理排位：它就站在自己组件渲染的前一格。设计收益有二：pre 回调里改派生状态可以并入同一次渲染（不引发双渲染）；父更新把子组件卸载时，直接跳过子已排队的 pre watcher（不做无效工作）。

**第三段（post 队列，主队列清空后）**：`mounted` / `updated` 钩子——注意它们的真身：**它们就是 post 回调**，不是什么魔法时刻。`flush: 'post'` 的 watch 回调也在这里。所以「post = 渲染之后」同样是物理排位。

于是你那道 dontKnow 的答案现在可以从结构**推出来**：pre watcher 排在自己组件渲染 effect 的紧前面 → 执行时自己的 DOM 必然是旧的。要新 DOM → `post`；要无批处理 → `sync`。

## Connect：两队列方向相反——你摸底的答案有了第二重解释

还记得你答对的「mounted 子先父后」吗？现在你能看到它的成因：主队列按**调度顺序**（父渲染 effect 先执行，执行中途才创建子的 job），而 post 队列的钩子按**完成顺序**入队——父渲染 effect 执行到一半就递归挂载了子，子的 mounted 先入队。**主队列父先子后，post 队列子先父后——不是矛盾，是两种序（调度序 vs 完成序）在两个队列里各自主宰。**你摸底记住的现象，现在挂在了机制上。

# N2-a — KeepAlive：离开，但不死亡

## Motivate

你已经握着地基 R3：卸载（unmount）是**摧毁性**的——DOM 移除、实例销毁、副作用全部清理。但看这个场景：一个后台管理页，用户在「仪表盘 ↔ 设置」两个 tab 间来回切。每次切走再切回，仪表盘组件被摧毁再重建——图表从头加载、滚动位置归零、没提交的表单草稿蒸发。摧毁-重建模型在这里是**错误的粒度**：离开是暂时的，状态应该是持久的。设计问题由此而来：**能不能让组件离开 DOM，但不死亡？**

## Establish：缓存 = DOM 与实例的分离

KeepAlive 包裹动态组件，被切走的组件**从 DOM 分离、整棵子树缓存在内存里，实例不销毁**。由此产生**第二对生命周期钩子**，而它们的语义是本节的钥匙——**叠加，而非替换**：

| 钩子 | 触发时机 |
|---|---|
| `onActivated` | **首次挂载**和**每次从缓存重新插入** |
| `onDeactivated` | **移入缓存**和**真正卸载** |

为什么首次挂载也算 activated、真正卸载也算 deactivated？这样设计是为了给「有副作用的代码」一个**统一的暂停/恢复挂点**——你写 `onDeactivated` 里的暂停逻辑时，不需要区分自己此刻是被缓存还是被销毁，两种「离开」都走同一个钩子。

而这套语义的直接推论就是工程上最著名的坑——**缓存期的泄漏面**：deactivated 时，实例与其全部 watcher / effect / computed **继续存活**（只是 DOM 分离了）。`setInterval`、事件监听、WebSocket 都在后台照跑；而挂在 `onUnmounted` 里的清理，要等到 LRU 淘汰（`max` 选项）或真实卸载才会执行。

## Connect

- **与 N1**：`onActivated` / `onDeactivated` 与 `mounted` / `updated` 同属 post 时机——重新插入也是一次渲染 flush，「激活」通知排在它之后。
- **与 R3**：挂载递归（子先父后）对缓存恢复同样成立——重新插入复用实例，但仍是一次挂载行为；且两个钩子对缓存树的**所有后代组件**同样生效。
- **伏笔**：KeepAlive 第一次向你展示了「**组件的逻辑存在**（实例）与 **DOM 存在**（挂载）可以分离」——这个思想在 N2-c 的 Teleport 会被推到极致。

# N2-b — Suspense：异步依赖的边界

## Motivate

组合式 API 里最自然的取数写法是什么？**setup 里直接 await**：`const data = await fetchUser(id)`——代码像同步一样线性，没有 then 链、没有 onMounted 里再取。但组件树是同步递归的：父挂载 → 子 setup 卡在 await → 这个位置的界面显示什么？undefined？闪一下？布局塌陷再弹回？工程里的传统解法（骨架屏状态机、v-if 加载态）全是**手动**胶水。设计问题：**能不能有一个声明式的边界，替整个子树等待异步依赖就绪**？

## Establish

`<Suspense>` 就是这个边界。它的机制：

1. 它在**内存中**渲染 default 插槽，同时监视其中两类**异步依赖**：async setup()（含顶层 await）与异步组件。
2. 遇到异步依赖 → 进入 **pending**，显示 fallback 插槽；**全部**解析完成 → 整体切换为 resolved，default 上屏。
3. **关键语义**（官方明文，也是最容易想错的地方）：只有 **default 插槽的根节点被替换**时才重新进入 pending——树中更深处**新增**的异步依赖**不会**触发它。Suspense 盯的是「根」这一个位置，不是全树扫描。
4. 回退 pending 时先显示**旧的 default 内容**（不是 fallback）——体验连续性：已看到的内容不闪掉，`timeout` 可控。
5. 边界性格：官方标注**实验性**（API 可能变）；自身无错误处理（须上层 `onErrorCaptured`）；嵌套时内层加 `suspensible` 可把异步处理整体委托给外层边界，否则内层自成边界，可能出现空节点与多次 patch。

## Connect

- **与 R3（挂载递归）**：Suspense 在挂载递归链上插了一道「await 闸门」——整棵子树 settle 后才作为整体参与挂载完成（post 时机的钩子才来）。
- **与 N2-a**：三件套有**标准嵌套顺序 Transition > KeepAlive > Suspense**——由外到内，它们各自改造「挂载/卸载」的一个维度：过渡改「怎么进出」，缓存改「离开是否死亡」，边界改「何时算就绪」。

# N2-c — Teleport：逻辑在左，DOM 在右

## Motivate

有一类 UI 元素「逻辑上属于这个组件，但视觉上必须去别的地方」：模态框要盖住全页（不能被父级 `overflow: hidden`、`z-index` 或 `transform` 关在角落——`position: fixed` 在有 `transform` 祖先时会失效）；通知条要统一挂进全局容器。CSS hack 不可靠；把模态框提升到根组件、再层层传 props 回来又毁掉内聚。设计问题：**组件的「逻辑归属」与「DOM 归属」能不能分开声明？**

## Establish

`<Teleport to="body">` 就是答案：内容渲染到 DOM 的另一处，但**组件逻辑树分毫不动**——

- 被传送的 Child **仍是 Father 的逻辑子组件**：props 照收、`emit` 照发、`provide/inject` 沿逻辑链照常注入、DevTools 里仍显示在逻辑位置。
- 约束很少：目标须在挂载时已存在（3.5+ 的 `defer` 可推迟解析）；同一目标多个 Teleport 按挂载顺序追加。

注意现在你手里有**两棵树**了：**逻辑树**（实例父子、作用域、依赖注入）与 **DOM 树**（渲染产物的物理位置）。KeepAlive 分离的是「实例存在 vs DOM 存在」；Teleport 分离的是「逻辑位置 vs DOM 位置」——同一个思想（组件的存在不必与 DOM 绑死）的两次实例化。N7 的 vapor 还会第三次动这对关系。

## Connect

- **R5（插槽 = 父作用域编译）**：传送的内容里若有插槽，仍按父作用域编译——编译归属逻辑树，落点归属 DOM 树，互不干扰。
- **一个易混点**：原生 DOM 事件（click 等）传送后**确实**沿物理层级冒泡（body 那边）；但 Vue 组件的 `emit` 从来不是 DOM 冒泡——它是逻辑树上「子实例 → 父实例」的直接调用。两套事件系统，两棵树各走各的。

# N4 — effectScope：「自动清理」的真身

## Motivate

先问一个你从没问过的问题：**为什么 setup 里写的 watch，组件一卸载就自动停了？** 谁在收拾？（你从第一天用 Vue 就享受这个服务，但它从没显形。）而 N2-a 刚给你看过它的边界失灵处：KeepAlive 缓存期清理不来。更一般的问题：**「自动清理」的管辖范围到底在哪里——什么时候它不罩着你？**

## Establish

真身是 **effectScope**，三条事实构成它的全部：

1. **setup() 本身就运行在一个 scope 里**。你写的每个 `watch` / `watchEffect` / `computed`，创建时都被**当前 scope 同步收集**。
2. **卸载 = `scope.stop()`**——递归停掉收集到的一切及嵌套 scope。「自动清理」不是魔法，是收集在起作用。
3. 这个能力被抽成了通用 API：`effectScope()` 让你在**任何地方**（组件外、Pinia store、router guard）拥有同样的「批量拥有、批量释放」；`effectScope(detached)` 创建脱离父 scope 的游离作用域（共享 composable 不随组件死亡）；`onScopeDispose(fn)` 是作用域版的 `onUnmounted`。

而它的**管辖边界**（RFC 明文承认的缺陷）：**收集是同步的**——async setup 里 `await` **之后**创建的 effect，逃逸收集。await 恢复执行时，「当前 scope」的同步上下文已经断了。工程界三大泄漏形态全是它的变体：await 后创建（composable 内）、事件处理器内延迟创建、无组件上下文的工具函数（Pinia action / router guard）中创建——后两者根本不在 setup 的同步段里。

## Connect

- **N2-a 的泄漏现在有了机制解释**：KeepAlive 缓存期 = 实例活着 = scope 没停 = 副作用照跑；你在 `onDeactivated` 里手动暂停，正是在 scope 之外手动接管。
- **N1**：副作用是调度队列的乘客，`scope.stop()` 从源头注销它们的乘车资格。
- **平台在吸收这个姿势**：Vue 3.5 给 `EffectScope` / `WatchHandle` 都加了 `pause()` / `resume()`——你在 N2-a 学的「暂停/恢复」手动姿势，正在变成一等公民 API。

# N6 — v-model 契约：双向的糖，单向的心

## Motivate

R4 给过你组件通信的完整闭环：数据向下（props）、事件向上（emit）。但表单控件是这个契约的**最高频消费者**——每个输入框都是「父传值下来 + 子报告新值上去」的固定搭配。3.4 之前子组件侧要手写三件套八股：props 定义 + emit 声明 + 中转 computed（get 读 prop、set 发事件）。设计问题：**能不能把这对固定搭配压成一个语法声明——同时不破坏单向流？**

## Establish

`v-model` 在组件上的全部真相是一次**编译期展开**：

```
<Child v-model="foo"/>
        ↓ 编译为
<Child :modelValue="foo" @update:modelValue="v => foo = v"/>
```

**没有新机制，没有新通道。** 在此之上：`v-model:title` 参数化出多路双向（prop `title` + 事件 `update:title`）；修饰符（`.trim` 等）经 `xxxModifiers` prop 传给子组件——元信息也走 prop，契约一致。

3.4 的 `defineModel()` 把子组件侧的八股也收掉：一行声明，编译展开为 prop + emit，返回一个**本地可写的 ref**——读是 prop 值，**写自动变成 emit**。支持命名参数、prop 选项（required / default）、解构取 modifiers、get/set 变换实现自定义修饰符。

**官方警告的坑**：`defineModel` 设了 `default` 而父级**未绑定值**时，父子失同步（父侧 undefined、子侧默认值）；可变引用类型的默认值必须包工厂函数——和你学过的 data 为什么是函数同一个理由。

## Connect

**和摸底第一题正面对照**——那道 `items.push` 题确认了你懂「props 传引用、子能钻空子直接改父的对象」。而 v-model **恰恰不是**这个：钻空子是「子伸手改父的对象」（引用直达、无人知晓）；v-model 是「子报告新值，**改父数据的仍然是父自己的代码**」（`v => foo = v` 在父组件里执行）。这就是「合法双向」与「非法双向」的分界——**双向的是约定，不是数据通路**。单向流从未被破坏，它只是被打包了。

# N7 — Vapor Mode：拆掉中介

## Motivate

你已经知道 VDOM 模式的完整链条（摸底 R1/R2）：状态变 → 渲染 effect 重跑 → 生成新 VDOM 树 → 新旧树 diff → patch 最小 DOM 操作。现在问一个从没问过的问题：**中间那棵 VDOM 为什么存在？**

答案是声明式的代价：模板声明的是「结果应该是什么」，要算出「具体改什么」，就需要新旧两份快照来对比。但 Solid/Svelte 给出了另一个洞察：**如果编译时就知道哪个状态连到哪个 DOM 节点，中介可以整个拆掉**——状态一变，直接调用那个节点的更新函数。Vapor 就是 Vue 版的这个转向。

## Establish

**核心机制**：编译期建立「状态 → DOM 更新调用」的精确直连。渲染 effect 不再产出 VDOM 树做对比，而是执行编译出的定点更新——一次状态变更，只有真正连接它的 DOM 节点参与。

**什么变了，什么没变**（对照你已建立的一切）：

| | 状态 |
|---|---|
| R1 响应式地基（属性访问收集依赖） | **不变，且更强**——3.6 换成 alien-signals 实现 |
| 组件契约 props / emit / slots | **保留**——vapor 组件间仍用同样的通信模型 |
| VDOM 树 / diff | **消失**——被编译期直连取代 |
| `getCurrentInstance()` | 返回 **null**（无公共实例代理） |
| `$el` / `$refs` 等实例暴露 | 不可用 |
| `v-memo` | 被忽略（告警）——它优化的是 diff，diff 没了 |
| Options API | 不支持 |
| 事件处理 | 委托到 document——祖先 `stopPropagation()` 会截断它 |

**现状**（researcher 一手核实的 2026-10 时点）：Vue **3.6 RC 阶段**（rc.12，10-16），功能完备、未发稳定版；第三方基准与 Solid / Svelte 5 同级；官方建议**局部采用**（性能敏感页）或小型新应用。互操作：VDOM 应用装 `vaporInteropPlugin` 后两类组件可互相嵌套——但边界情况未穷尽，官方建议分区使用、避免深度混嵌。

## Connect：两个树的终章

N2-c 你建立了「逻辑树与 DOM 树」的分离。现在把时间线拉全：**KeepAlive** 分离了实例存在与 DOM 存在；**Teleport** 分离了逻辑位置与 DOM 位置；**Vapor** 干掉了夹在中间的 VDOM 中介——逻辑树直连 DOM 树。三次演进，同一个思想的三个刻度：**组件的存在与它的 DOM 投影，绑定得越来越松**。而响应式地基（你在摸底就握住的那个「属性访问即追踪」）从头到尾没动——同一地基，两种房子。

## Quiz-check


> [!question] Quiz
> vapor 组件里 `v-memo` 被忽略（3.6 会告警）。它在 VDOM 模式下的作用是跳过子树 diff。它在 vapor 下失去意义的根本原因是？
>
> 1. memo 依赖的响应式 API 在 vapor 里不存在
> 2. DOM 更新太快，memo 的缓存开销反而更大
> 3. 没有 diff 环节可跳过——更新本来就只发生在精确连接的节点上
> 4. vapor 禁止使用指令


> [!success] Quiz — correct ✓
> Your answer: 3. 没有 diff 环节可跳过——更新本来就只发生在精确连接的节点上
> Correct answer: 没有 diff 环节可跳过——更新本来就只发生在精确连接的节点上
>
> v-memo 的全部价值是「让 reconciler 跳过已知未变子树的 diff」——它优化的是 diff 这个中间环节。vapor 把中间环节整个拆了：编译期已建立状态到 DOM 节点的精确连接，一次变更只触发所连节点的更新调用，其余节点根本不参与。「没有 diff，就没有 diff 可跳过」——不是性能权衡（「更新太快不值得缓存」把机制消解误读为成本核算），是机制性失效，如同电梯拆了之后「等电梯」的建议自然作废。指令在 vapor 里仍然存在（另一套函数式接口），响应式地基也仍在（alien-signals）——消失的只有 VDOM 中介。

## 1. 四个步骤的含义

它们是 teach 技能里**逐节点授课循环**的固定四拍（Phase 3 — Teach 的骨架）。背后的世界观：知识不是背下来的清单，是一张**依赖图**——每个新事实都应该被「有动机地给出、可接受地立起、连到既有基础上、确认真正锁入」。四拍就是这句话的执行：

**Motivate（动机）** — 框定「为什么**现在**需要这个节点」：你手头的什么问题逼它出现。不是「因为大纲下一个是它」，而是缺口自己显形。实例：N1 的 Motivate 是把你 dontKnow 的那道题摆回桌上——断点自己说明课程为什么从这里开始；N7 的 Motivate 是问「中间那棵 VDOM 凭什么存在」。

**Establish（建立）** — 把节点本身立起来。两种立法：**无条件真理**（可以当面接受、无附加条件的事实，直接陈述——如「pre 的名字就是答案」）；**派生步骤**（从你已建立的事实出发，走一条「你本可以自己发现它」的推导路径——如 N6 的编译展开、N1 的死锁反证）。

**Connect（连接）** — 把新节点**显式挂到**已建立的节点上，画出依赖图的新边。这是「理解 = 连接」的落地动作。实例：N2-c 回收 N2-a 的伏笔（「逻辑存在与 DOM 存在分离」→「逻辑位置与 DOM 位置分离」）；N7 把 KeepAlive、Teleport、vapor 串成同一个思想的三次演进——那一节的 Connect 就是全课程最大的一条边。

**Quiz-check（评分确认）** — 用 graded quiz 确认节点**真正落地**，而不是「讲过了就算会了」。它带着一条硬规则：未通过的节点不作为后续构建的基础。实例：N1 四连败后我们停下修复、不硬讲 N2，就是这条规则在执行；反过来 N2 三小节全一次通过，才允许 N4 开讲。

一句话：**Motivate 给它出生的理由，Establish 给它身体，Connect 给它位置，Quiz-check 给它户口。**

## 2. 为什么是英文

诚实的技术性答案：**这是移植的忠实性选择，不是教学设计的选择。** 这套术语骨架（含 probe / plan / teach 三阶段名）直接来自 `tmp/learn` 原仓库的 SKILL.md——原作者（amosblomqvist）用英文写的；任务 1.2 移植时保留了英文术语，授课时我只把正文完全中文化。当时保留的理由有一个真实的：术语作为**跨会话锚点**——TCP 场和 Vue 场、课程日志、tasks.md 恢复点里都用同一套标题，你在日志里回看时四拍的轨迹是可追踪、可对齐的。

但你指出的不一致是真的：**标题语言没有跟随你的提问语言**。四拍的概念完全可以中文化，比如：

| 英文 | 可选中文 |
|---|---|
| Motivate | 动机 / 为何在此 |
| Establish | 建立 / 立起 |
| Connect | 连接 / 挂靠 |
| Quiz-check | 验收 / 确认 |

（probe / plan / teach 对应 摸底 / 规划 / 授课——这三个我授课时其实一直在用中文。）
